# OLX.pl Telegram-бот

## Структура

```
olx_telegram_bot/
├── bot.py          # Главный файл (long polling)
├── parser.py       # Парсер OLX (JSON + HTML fallback + параллельные детали объявления)
├── config.py       # Настройки (токен, паузы, лимиты, параллельность)
├── filters.py      # Меню /filters и применение фильтров (без изменений)
├── history.py      # НОВОЕ: история отправленных объявлений (дедупликация)
├── requirements.txt
├── Procfile        # для Render/Railway (worker: python bot.py)
└── olx.txt         # создаётся автоматически при первом парсинге
```

## Как это работает

1. Пользователь пишет боту `/parse <ссылка или ключевое слово> [лимит]`.
2. Парсер обходит страницы выдачи OLX.pl (пагинация), сначала пытаясь
   вытащить встроенный JSON с данными объявлений, а если не получилось —
   разбирает HTML через BeautifulSoup (несколько наборов селекторов).
3. Объявления, которые уже отправлялись этому чату раньше (через /parse
   или /monitor), пропускаются — парсер листает страницы дальше, пока не
   наберёт нужное количество НОВЫХ объявлений (см. `history.py`).
4. Детали объявлений (продавец, доставка, локация) дозапрашиваются
   ПАРАЛЛЕЛЬНО — пачками по `config.DETAIL_CONCURRENCY` штук одновременно,
   а не строго по одному, как раньше.
5. В чат уходят объявления (фото + текст, с ценой и датой публикации в
   формате "01.08.2026 21:14 (3 часа назад)"), а следом — файл `olx.txt`
   со всеми найденными объявлениями.

## Что изменилось в этой версии

### 1. Объявления больше не повторяются (`history.py`)
Раньше повторный `/parse` по тому же запросу мог снова прислать те же
самые объявления. Теперь бот запоминает (в памяти процесса, по `chat_id`)
ссылки всех объявлений, которые уже были отправлены — через `/parse` ИЛИ
через `/monitor`, это общая история. При поиске такие объявления
пропускаются, а парсер автоматически листает дальше по страницам, чтобы
всё равно набрать запрошенный лимит НОВЫХ объявлений.

Новая команда **`/resetseen`** — забыть историю и снова увидеть уже
показанные объявления (например, если хотите начать поиск "с нуля").

Как и фильтры, эта история хранится в памяти процесса — слетает при
передеплое/перезапуске сервиса. Если это станет проблемой, следующий шаг —
перенести её (вместе с фильтрами) в SQLite/Redis.

### 2. Ускорение парсинга (`config.DETAIL_CONCURRENCY`)
Самая медленная часть парсинга — дозапрос страницы КАЖДОГО объявления за
данными продавца. Раньше это делалось строго по одному, с паузой между
запросами. Теперь такие запросы идут пачками — по умолчанию 4 объявления
параллельно (переменная окружения `DETAIL_CONCURRENCY`, можно менять),
что ускоряет эту часть примерно в 4 раза. Пауза между запросами и ротация
User-Agent сохранены — просто несколько таких "потоков" работают
одновременно. Если после этого начнутся частые 403/429 от OLX — уменьшите
`DETAIL_CONCURRENCY` до 2-3.

Дополнительный источник ускорения — та же дедупликация: объявления,
которые уже были показаны, вообще не попадают в список на дозапрос
деталей, то есть на них не тратятся лишние HTTP-запросы.

### 3. Цена и дата публикации — теперь добираются и с самой страницы объявления
Раньше цена/дата брались только с карточки в выдаче (JSON или HTML
селекторы страницы поиска) — если OLX там их не отдавал (смена вёрстки,
не сработавшие селекторы), в чат уходило "Цена не указана" / "не указана",
хотя сама страница объявления показывала эти данные.

Теперь, раз бот всё равно заходит на страницу объявления за данными
продавца, он заодно пытается добрать оттуда и цену, и дату — **пятью
способами по очереди**, пока один не сработает:
1. встроенный JSON самого объявления на детальной странице;
2. JSON-LD разметка (`<script type="application/ld+json">`);
3. meta-теги (`og:price:amount` / `product:price:amount`);
4. CSS-селекторы на странице объявления (`data-testid="ad-price-container"`,
   `data-testid="ad-posted-at"` и т.п.);
5. запасной текстовый поиск "N zł" в начале страницы.

Если карточка выдачи и так дала цену/дату — повторный запрос на детальную
страницу их не трогает (перезаписи хорошими данными не будет).

Итоговый вид в чате — цена и дата сразу под названием товара:

```
Товар: ...
Цена: 1500 zł
🕒 Опубликовано: 03.08.2026 14:20 (2 часа назад)
Местоположение товара: ...
```

Формат даты — точное время (по варшавскому времени, OLX.pl — польский
сайт) плюс относительное "N назад" в скобках. То же самое попадает и в
файл `olx.txt`.

**Если у конкретных объявлений цена/дата всё равно не находятся** — значит,
ни один из пяти способов не сработал (OLX очень сильно поменял вёрстку).
В логах сервиса при этом появится предупреждение вида "Не удалось
определить цену/дату для <ссылка>" — по нему и по актуальному "Просмотру
кода страницы" на olx.pl проще всего понять, какой CSS-селектор/JSON-путь
нужно поправить в `parser.py` (`DETAIL_PRICE_SELECTORS`,
`DETAIL_DATE_SELECTORS`, `_extract_ad_object_from_json`).

Меню `/filters` и вся логика самих фильтров (категория, цена, период,
доставка, банворды, фильтры продавца) — **не менялись**.

## Локальный запуск

```bash
python -m venv venv
source venv/bin/activate      # Windows: venv\Scripts\activate
pip install -r requirements.txt

export TELEGRAM_BOT_TOKEN="ваш_токен_от_BotFather"   # Windows: set TELEGRAM_BOT_TOKEN=...
python bot.py
```

## Деплой на Render (free plan)

Free-тариф Render не даёт Background Worker, только **Web Service** —
поэтому в `bot.py` встроен маленький Flask-сервер, который просто отвечает
"OK" на порту, который Render передаёт через переменную `PORT`. Сам бот
как работал через long polling, так и работает — в отдельном потоке.

1. Залейте проект в GitHub-репозиторий (файлы `bot.py`, `parser.py`,
   `config.py`, `filters.py`, `history.py`, `requirements.txt` —
   обязательно **в корне** репозитория, не во вложенной папке).
2. Render → **New** → **Web Service**, подключите репозиторий.
3. Runtime: Python 3.
4. Build Command: `pip install -r requirements.txt`
5. Start Command: `python bot.py`
6. Environment → добавьте переменную `TELEGRAM_BOT_TOKEN` (значение — токен
   от BotFather). При желании — `DETAIL_CONCURRENCY` (по умолчанию 4).
7. Deploy.

**Про "спин-даун" на free-плане.** Render усыпляет бесплатный Web Service
после ~15 минут без HTTP-запросов на его URL. Наш бот всё равно продолжит
получать сообщения через Telegram polling, пока не уснёт процесс целиком —
то есть первое сообщение после долгого простоя может прийти с задержкой
~50 секунд (это время холодного старта). Если это критично, можно каждые
10-14 минут дёргать `https://ваш-сервис.onrender.com/` бесплатным
пинг-сервисом (например, UptimeRobot) — тогда сервис не будет засыпать.

## Деплой на Railway

1. Залейте проект в GitHub, импортируйте репозиторий в Railway.
2. Railway сам подхватит `Procfile` (`worker: python bot.py`).
   Если создаст Web-сервис по умолчанию — вручную укажите Start Command
   `python bot.py` и уберите привязку к порту (боту порт не нужен).
3. В Variables → добавьте `TELEGRAM_BOT_TOKEN`.
4. Deploy.

## Важные оговорки

- **OLX регулярно меняет вёрстку и защиту от ботов.** Я заложил запасные
  селекторы и попытку читать встроенный JSON, но раз в какое-то время
  парсер всё равно может потребовать обновления селекторов в `parser.py`
  (см. `CARD_SELECTORS`, `DETAIL_SELLER_SELECTORS`, `DETAIL_DELIVERY_SELECTORS`).
- **Бесплатные хостинги (Render/Railway free tier)** могут "усыплять"
  сервис при простое или ограничивать исходящий трафик — если бот перестал
  отвечать после долгого бездействия, проверьте логи сервиса.
- **Без прокси.** Если OLX начнёт стабильно возвращать 403/429 с IP вашего
  хостинга, потребуется добавить ротацию прокси — в текущей версии её нет,
  только ротация User-Agent, задержки между запросами и ограниченная
  параллельность (`DETAIL_CONCURRENCY`).
- **История отправленных объявлений и фильтры — в памяти процесса.**
  Слетают при передеплое/перезапуске. Что доделать в первую очередь при
  росте нагрузки — перенести оба в SQLite или Redis.
- Используйте парсинг ответственно: не завышайте лимиты, не убирайте
  задержки и не задирайте `DETAIL_CONCURRENCY` слишком высоко — это
  увеличивает риск блокировки IP хостинга.
